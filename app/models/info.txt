user.py — email gets unique=True, index=True so login lookups are fast and duplicate emails are rejected at the DB level, not just the service layer.

career_path.py — user_id gets unique=True to enforce the 1:1 relationship from your ER diagram (one user → one active path). generated_by_ai defaults to True since the proposal says all paths go through the AI engine.

skill.py — unlock_at is Optional[datetime] and starts as None. The service layer sets it the moment the user first touches that skill. status defaults to "locked" because skills only open based on level.

project.py — skills_needed is stored as a comma-separated string ("Python, Docker") matching your ER diagram. You can normalise this into a join table later in a future sprint without changing the model interface.

resource.py — level_range is stored as "1-10", "11-20" etc. (a string, exactly as shown in the ER diagram). Your service layer will split it on - to get min_level and max_level for the unlock check.

milestone.py — achieve_date is Optional and starts None — it only gets stamped when xp_service.check_level_up() triggers it. badge_icon is also Optional since not every milestone needs a visual badge.

__init__.py — imports models in dependency order (parent tables before child tables). This is critical for two reasons: Alembic needs to see all tables before generating migrations, and SQLModel needs all classes loaded before it can resolve forward-reference strings like "CareerPath" in relationship definitions.
